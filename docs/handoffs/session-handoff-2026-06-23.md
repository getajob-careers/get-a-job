The browser agent's current role
This is worth its own paragraph because the work has evolved.
Initially the browser agent was used for company-name discovery: feed it a sector-targeted list, ask it to find each company's careers page, identify the ATS. That produced batches 1-3 (banks, insurance, telecom, Big 4, consulting, FMCG, retail, law firms). The yield curve was modest — most non-tech Israeli companies build custom career sites, and we already had most major supported-ATS employers in the registry.
The browser agent's most valuable use turned out to be network-call inspection — opening a careers page in DevTools, watching XHR/Fetch on initial load, identifying whether the page is backed by a clean public JSON endpoint, an auth-gated JSON endpoint, server-rendered HTML, or a WAF challenge. CC can't do this from an HTTP-only fetcher because SPA data binds after JS execution. The 29-company JSON-endpoint check (which produced One Zero and HOT) was exactly this kind of work.

Key principles being applied

Yield gates fetcher work. ATS-vendor investigations require independent evidence of 4+ Israeli tenants with current postings before any build investigation begins. (The lesson from Teamtailor 1 tenant, iCIMS 0 Israeli enterprises, Hunter HRMS 1 new viable tenant, Umbraco 2 incompatible tenants.)
Vendor brand identity is unreliable signal. Applies to ATS vendors AND to shared CMS infrastructure. A shared vendor brand does not imply a shared API surface. Future shared-infrastructure investigations require independent evidence of both (a) a shared API and (b) 4+ Israeli tenants reachable from it.
Per-publisher JSON endpoints are a legitimate tier. The Bezeq pattern (custom career site fetching from a publisher-built public JSON endpoint on the company's own domain) sits closer to ATS-direct than to scraping. Each one is a small per-publisher fetcher; the bezeq_native / hot_native slug naming distinguishes per-publisher from multi-tenant.
The legal floor is firm. No aggregator scraping (AllJobs, Drushim, etc.), no LinkedIn scraping, no anti-bot evasion (WAF bypass, Playwright fingerprint randomization). Tier 4 work is held pending Eli's wife's legal review (separate thread, unrelated to today's work).
Independent verification. Every CC PR is verified against the live Supabase DB via MCP before merge. Past sessions caught contamination issues (rebake harness pollution, etc.) only because of this rule.
